# 技术说明：seekdb 端侧迷你知识库

## 1. 模型与量化

- 模型：**Xenova/bge-small-zh-v1.5**（BAAI bge-small-zh-v1.5 的 ONNX 转换版，Transformers.js 格式），
  来源 <https://huggingface.co/Xenova/bge-small-zh-v1.5>，镜像 <https://modelscope.cn/models/Xenova/bge-small-zh-v1.5>。
  512 维，CLS 池化 + L2 归一化，中文语义检索表现稳定。
- 三种精度均由同一仓库的官方 ONNX 文件提供，运行时按 `dtype` 直接加载对应权重，不做二次转换：
  `fp32 → onnx/model.onnx`、`fp16 → onnx/model_fp16.onnx`、`q8(INT8) → onnx/model_quantized.onnx`。
  量化方式为 ONNX 动态/静态 INT8 量化（权重 8 bit + 缩放因子），FP16 为半精度权重。
- 模型体积（同一口径，仅统计 ONNX 权重文件）：

  | 精度 | 体积 | 相对 fp32 压缩比 |
  | --- | --- | --- |
  | fp32 基线 | 90.5 MiB（94.85 MB） | 1.00× |
  | fp16 | 45.3 MiB（47.50 MB） | **2.00×** |
  | INT8 (q8) | 22.9 MiB（24.01 MB） | **3.95×** |

- 检索质量（30 篇语料 / 12 条查询，文档级 Recall@5、nDCG@5，详见测试报告）：
  fp32-WASM `1.000 / 0.974`，INT8-WASM `1.000 / 0.974`（无下降），FP16-WebGPU `1.000 / 0.974`。
  INT8-WebGPU 下降到 `0.750 / 0.600`：该量化模型的部分算子在 WebGPU 上回退到 CPU，
  数值路径不一致且不提速，因此**推荐组合是 WebGPU + FP16、WASM + INT8**，界面默认也按设备自动选择。

## 2. 端侧运行

- 运行时：Transformers.js 3.7.5 + ONNX Runtime Web（WebGPU 走 `jsep` 版 wasm，WASM 走 SIMD 多线程）。
  推理放在 Web Worker，主线程只做 UI，向量化过程中界面不卡顿。
- 后端选择：先 `navigator.gpu.requestAdapter()` 探测；可用则 `device: "webgpu"`，并在界面顶部显示
  `推理后端 WEBGPU`。加载或推理抛错时捕获并自动重建 `device: "wasm"` 的会话，同时把降级原因写进状态与页面提示。
  用户也可在下拉框强制指定后端，便于复现对比。
- 本地优先：模型文件由 `scripts/fetch-models.mjs` 预取到 `models/`，服务端以静态资源提供，
  `env.allowRemoteModels=false`，因此评测环境不依赖外网；也支持 `MODEL_HOST` 直连 HF / hf-mirror。
- 计时：模型加载、预热、文档向量化、写入、索引刷新、查询向量化、检索、端到端全部在页面内记录，
  基准测试结果可导出 JSON（`bench/results/*.json`）。

## 3. seekdb 使用

- 接入方式：`seekdb-js 1.4.0`，默认**嵌入式文件模式**（`SEEKB_PATH=./data/kb.db`，无需 Docker），
  也支持 `SEEKB_HOST/PORT` 连接本地 seekdb server，代码路径不变。
- 集合结构（每个知识库一个 collection）：

  ```sql
  CREATE TABLE c$v2$<id> (
    _id VARBINARY(512) PRIMARY KEY,
    document STRING,            -- 分块原文
    embedding VECTOR(512),      -- 浏览器产出的归一化向量
    metadata JSON,              -- docId / title / source / chunk / createdAt
    FULLTEXT KEY idx_fts (document) WITH PARSER ngram PARSER_PROPERTIES=(ngram_token_size=2),
    VECTOR KEY idx_vec (embedding) WITH (DISTANCE=COSINE, TYPE=HNSW, LIB=VSAG, M=16,
                                        EF_CONSTRUCTION=200, EF_SEARCH=64)
  );
  ```

- 混合检索：`DBMS_HYBRID_SEARCH` 在库内执行。服务端把查询写成
  `{"query":{"query_string":{...}},"knn":{...},"rank":{"rrf":{"rank_window_size":64,"rank_constant":60}},"size":k}`，
  由 `GET_SQL` 生成**一条 SQL**，同一条语句里完成 `MATCH ... AGAINST` 全文召回、
  `cosine_distance` 向量召回、RRF 融合与排序；前端只收到最终排序，不存在客户端拼两路结果。
- 嵌入式构建的 HNSW 近似索引在 1.4.0 上暂不可查询（`SYNC_MODE=SYNC` 不支持，异步索引不生效），
  因此在嵌入式模式下把生成 SQL 中的 `APPROXIMATE` 关键字去掉，让 seekdb 在**同一条语句内**做精确向量扫描，
  融合仍在库内完成。设置 `SEEKB_APPROXIMATE=1` 可恢复原生近似路径（server 模式推荐）。
  这是唯一一处针对性适配，已在 README 中注明。
- 写入与刷新：`collection.upsert()` 批量写入后立即 `collection.refresh_index()`，
  接口返回 `writeMs / refreshMs`；冒烟测试验证「写入 → 刷新 → 新文档可检索」。

## 4. 状态与优化

- 集合/会话状态：多知识库（collection）管理，集合与向量维度绑定，切换模型后新建集合；
  当前集合持久化在 `localStorage`，重启后自动恢复；导入为增量 upsert，同一分块 ID 不会重复。
- 分块：按句号/问号/换行等边界切分，默认 400 字符、60 字符重叠，块保留 docId/title/chunk 元数据。
- 批处理：文档按 16 条一批送入 Worker；查询单条推理。实测 FP16+WebGPU 下批大小 1→16
  吞吐从 14.4k 提升到 46.8k 字/秒（3.2×），批 32 无进一步收益，故默认 16。
- 索引刷新策略：以「一次导入请求」为刷新单位（每 400 块一批），避免逐条刷新；
  30 块的刷新成本约 0.3–0.4 s（冷启动首次 2.3 s）。

## 5. 实测结果

设备：Apple Silicon macOS（Metal-3），Chrome 156（headless），30 篇中文语料 / 30 块 / 12 条查询，
分块 240 字符、重叠 40，数据全部由页面内基准测试脚本实测（`npm run bench`，取 12 次查询中位数）。

| 配置 | 模型体积 | 文档向量化 | 写入+刷新 | seekdb 检索 | 查询端到端 | Recall@5 | nDCG@5 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| fp32 + WASM（基线） | 90.5 MiB | 1.56 s / 2.1k 字·s⁻¹ | 72 + 324 ms | 2.19 ms | 13.2 ms | 1.000 | 0.974 |
| INT8 + WASM | 22.9 MiB | 1.60 s / 2.1k 字·s⁻¹ | 70 + 428 ms | 2.09 ms | 14.1 ms | 1.000 | 0.974 |
| FP16 + WebGPU | 45.3 MiB | 73 ms / 45.3k 字·s⁻¹ | 77 + 426 ms | 2.27 ms | 13.4 ms | 1.000 | 0.974 |
| INT8 + WebGPU | 22.9 MiB | 1.64 s / 2.0k 字·s⁻¹ | 80 + 318 ms | 2.30 ms | 24.4 ms | 0.750 | 0.600 |

冷启动（禁用 HTTP 缓存、全新浏览器配置）：INT8+WASM 6.1 s、FP16+WebGPU 4.1 s（含 ONNX 会话创建与着色器编译）；
预热后重新加载模型 0.2–0.4 s。查询向量化中位数 WASM ≈9–10 ms、WebGPU ≈9 ms（FP16）。
