# 验证样例 T-001：订单查询支持状态与金额下限过滤

评审用样例。全部操作在 `minimax/` 目录内完成，12 步一键执行（`bash scripts/run_demo.sh`），也可按本节命令单步复核。
每步的**预期结果**都写成可机械核对的条件（`grep` / 退出码 / JSON 字段），与 `evidence/` 中的产物一一对应。

## 1. 任务描述（`samples/task-T001.md`，原文）

```
# 任务 T-001：订单查询支持状态与金额下限过滤
task_id: T-001
description: |
  业务需求：客户成功团队需要在客服后台按“状态 + 金额下限”筛选订单。
  请修改订单服务的查询能力，使其支持按订单状态与金额下限过滤（具体约束以“适用的规格条目”为准），
  并保证既有查询行为与兼容性约束不被破坏。
```

任务描述里**不含任何具体接口签名或规格编号** —— “要改什么、按哪条规格改、用什么测试验收”必须由系统从 seekdb 检索出来的规格中给出，这是本样例的核心考察点。

## 2. 规格与编号

| 规格文档 | 版本 | 条目 | 作用 |
|---|---|---|---|
| `demo_project/specs/SPEC-order-query.md` | v1（初始） | ORD-001 按客户查询 / ORD-002 空结果 / ORD-003 确定性排序 | 必须保持的既有行为（回归约束） |
| `samples/spec_update/SPEC-order-query.md` | v2（step5 覆盖为同名文件） | 在 v1 三条基础上新增 **ORD-004 状态与金额下限过滤**、**ORD-005 非法状态拒绝** | 本任务要实现的新能力；v1 条目原文未变 |
| `demo_project/specs/SPEC-order-core.md` | v1 | ORD-CORE-001 状态枚举 / ORD-CORE-002 金额单位（整型分）/ ORD-CORE-003 调用兼容（位置参数不变） | 跨模块硬性约束 |
| `demo_project/specs/SPEC-refund-boundary.md` | v1 | REF-001 退款金额边界 / REF-002 退款状态限制 | 同工程其他能力的回归范围 |

**ORD-004 要点**：`list_orders` 新增可选参数 `status`、`min_amount`；`status` 大小写不敏感并去首尾空白，空串/`None` 表示不过滤；`min_amount` 为包含式下限（`total_amount >= min_amount`）；过滤后仍满足 ORD-001 与 ORD-003；新参数必须带默认值以满足 ORD-CORE-003。
**ORD-005 要点**：`status` 不在 `models.STATUS_SET` 内（如 `archived`）时抛出含错误码 `INVALID_STATUS` 的 `ValueError`，禁止静默返回全部订单。

## 3. 被测业务工程初始状态（v1 实现）

- `src/order_service/service.py::list_orders(customer_id, repository=None)` —— **只支持按客户过滤**，未实现 ORD-004/005。
- `src/order_service/models.py` —— `STATUS_SET = {pending, paid, shipped, cancelled}`，金额一律整型分。
- `src/order_service/repository.py::list_by_customer` —— 按 `created_at` 升序、同秒按插入顺序。
- 固定样例数据 `service.SAMPLE_FIXTURES`（`reset_repository()` 每次测试前重建，保证前后数据集一致）：

| order_id | customer_id | total_amount | status |
|---|---|---|---|
| ord-0001 | c1 | 500 | pending |
| ord-0002 | c1 | 1500 | paid |
| ord-0003 | c1 | 900 | paid |
| ord-0004 | c1 | 2000 | shipped |
| ord-0005 | c1 | 100 | cancelled |
| ord-0006 | c2 | 3000 | paid |

- **目标测试** `tests/test_order_filter_target.py`（6 例，全部依据 ORD-004/ORD-005）：`test_filter_by_status`、`test_status_case_insensitive_and_trimmed`、`test_status_empty_or_none_means_no_filter`、`test_min_amount_filter`、`test_invalid_status_raises_error_code`、`test_combined_filters_keep_deterministic_ordering`。
- **回归测试** `tests/test_orders_regression.py`（8 例，覆盖 ORD-001/002/003、ORD-CORE-003、REF-001/002 及建单/取单）：`test_create_and_fetch_order`、`test_create_order_rejects_float_amount`、`test_list_orders_by_customer`、`test_list_orders_empty_customer`、`test_list_orders_ordering_stable`、`test_list_orders_positional_compat`、`test_refund_invalid_amount_raises`、`test_refund_only_paid_or_shipped`。

> 两个测试文件在修改前后**保持完全不变**（`verify` 报告里的 `file_sha256` 前后相同即可核对）；修改前的失败是**功能性失败**（`TypeError: list_orders() got an unexpected keyword argument 'status'` 等），不是导入/环境错误 —— 目标测试只使用工程内已有的可导入名称。

## 5. 重置方法（回到可重复验证的初始状态）

```bash
bash scripts/reset.sh              # demo_project 回初始快照 + 清空 seekdb（保留 PowerContext 状态）
bash scripts/reset.sh --pc-reset   # 额外清空 PowerContext 任务状态（回到 step1 的“完全空状态”）
bash scripts/run_demo.sh           # 再跑一遍，evidence/ 被新一批产物覆盖
```

`run_demo.sh` 自身在开头也会做 step0/step1 的清理（`FRESH_PC=1`），因此**同一份代码可以反复验证且每次结果一致**；模型输出内容可能有细微差异，但 step9 的测试结论恒为「目标 6 过 + 回归 8 过」。
