# 一页技术说明 —— 规有所依：SDD 上下文管理系统

**定位**：规格（Spec）是系统演进的唯一依据。本作品把「规格 + 代码 + 测试」放进 **seekdb** 做混合检索，把「任务进展 + 待办 + 验证结果」放进 **PowerContext** 做跨进程复用，把「按规格改代码」交给 **MiniMax** 真实执行；三者由一个统一 CLI（`sddctx`）串成可验证的闭环。

## 1. 模块结构（`sdd_context/`，1298 行，全部可离线复现）

```
samples/task-T001.md ─┐
demo_project/{specs,src,tests} ─┤
                                ├─ ingest.py ──► seekstore.py ──► seekdb（.sdddata/seekdb.db）
                                │  按 ## 规格编号 / AST 符号切块      全文(IK) + HNSW 向量 + RRF
                                │  内容哈希增量：新增/更新/删除
   cli.py（唯一入口）─► context_builder.py ─┬─ 混合检索 spec/code/test 三类
                                            ├─ 规格内“关联代码/验证”二次定位
                                            ├─ state.py ─► PowerContext Server（atomic-memory）
                                            └─ provenance 逐条核验来源真实存在
                        └─► patcher.py ◄── minimax_client.py（MiniMax chat completions）
                        └─► verify.py（pytest 目标/回归 + 命令/退出码/代码哈希留痕）
```

| 文件 | 职责（一句话） |
|---|---|

## 2. 上下文选择流程（为什么“规有所依”）

1. **检索即依据**：任务描述分别对 `spec` / `code` / `test` 三类做 seekdb `hybrid_search`（`$contains` 全文 + 向量，RRF `rank_window=30, constant=20`），命中什么由数据库决定，代码里不写死任何条目清单。
2. **整份规格生效**：命中某规格文件后，用 `collection.get(where={kind:'spec',source:文件})` 把该文件其余条目并入 —— 同一文档的条目通常整体适用（v2 引入 ORD-004/005 后，v1 的 ORD-001~003 仍作为回归约束被带入上下文）。
3. **规格决定改哪个文件**：从规格正文里的 `src/...py::symbol`、`tests/...py` 引用精确定位「需要修改的代码」和「用哪些测试验证」，来源标注为 `spec:ORD-004` 之类。
4. **内容取当前工作副本**：条目文本取自 seekdb（保证“更新后重新导入即生效”），代码/测试正文取自磁盘当前文件并带 sha，避免模型拿着过期副本改。
5. **状态参与上下文**：从 PowerContext 读取该任务最新的 `phase/done/todo/results`，写进上下文并交付给模型 —— 已完成事项不会被重复要求，验证结果会被引用。
6. **可核验**：`provenance` 逐条检查“输出的每个来源文件存在、规格编号能在原文里找到”，缺失即 `context` 返回退出码 4。

## 3. 三项技术分工（不允许互相替代）

| 技术 | 承担 | 证据 |
|---|---|---|
| **seekdb**（pyseekdb 1.4.0.post1，嵌入式） | 工程资料与索引的存储 + 全文/向量混合检索 + 增量更新；上下文内容由它决定 | `step2/step5` 摄取统计、`step12_dbq_*.json` 真实查询、`step4/6/11` 上下文里的 `retrieval` 日志与 `db_path` |

## 5. 关键取舍

- **向量用确定性哈希而不是下载模型**：评审从干净环境执行，检索不能卡在模型下载或外网；关键词质量由 seekdb 全文索引（IK）保证。
- **规格演进用「改文件 + 重新 ingest」而非重建库**：走真实的增量更新路径（`added/updated/removed`），证明“更新后的内容”确实来自数据库的新版本。
- **状态一律走 PowerContext API**：`sdd_context` 自己不写状态文件，`reset` 也不动状态，确保「重启后仍能读取并复用」是 PowerContext 在做的事。
- **模型输出必须过白名单**：`patcher.py` 只允许写上下文里出现过的代码文件，越界、新增文件、改测试/规格一律拒绝 —— 「MiniMax 真实参与」不等于「放任模型乱改」。
- **证据与代码同仓提交**：`evidence/` 与 `demo_project/`（修改后状态）来自同一次 `run_demo.sh`，评审可交叉核对。
