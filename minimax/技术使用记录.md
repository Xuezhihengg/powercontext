## 1. seekdb 的使用（数据库实际参与存储与检索）

**用法**：工程资料（规格 / 代码 / 测试）切块后写入 seekdb，上下文构建时的检索完全由 seekdb 返回结果决定。

| 环节 | seekdb 能力 | 代码位置 | 证据 |
|---|---|---|---|
| 建库建集合 | `AdminClient` + `Client(path=...)` 嵌入式模式；`Schema(vector_index=HNSW(dim=256, cosine), fulltext_index=analyzer "ik")` | `sdd_context/seekstore.py::SeekStore.__init__` | `step2_init.json`（`db_path`、`collection`） |
| 写入 | `collection.upsert(ids, documents, metadatas)`，metadata 带 `kind/source/req_id/symbols/sha` | `seekstore.upsert`、`ingest.ingest` | `step2_ingest_specv1.json`、`step5_ingest_specv2.json` |
| 删除消失的块 | `collection.delete(ids)`（规格条目被撤下时同步） | `ingest.ingest` 的 `removed` | `step5`（`removed=0`，v2 是新增不删旧） |
| 混合检索 | `collection.hybrid_search(query={"$contains": 任务文本, where kind}, knn={"query_texts": ...}, rank={"rrf":{...}})` | `seekstore.hybrid` | `step12_dbq_spec/code/test.json`、上下文里的 `retrieval.queries[*].returned_ids` |
| 精确取回 | `collection.get(where={"kind":"spec","source":文件})` 做同规格文件整体扩展 | `seekstore.fetch_by_source` | `step4/6/11` 的 `retrieval.queries` 中 `engine="seekdb.get"` 记录 |
| 增量更新 | 按块内容 sha256 判定 added / updated / unchanged / removed（规格 v1→v2 只重写变化的块） | `ingest.ingest` + `.sdddata/manifest.json` | `step5`：`added=2, updated=1, unchanged=17` |

**关键结论的落点**：
- 库中确有资料：`source_count_in_seekdb` = 18（v1）→ 20（v2），见 `step4/step6/step11_context_*.json`。
- 检索结果被真实使用：`step4/step6` 的 `applicable_specs[*].text` 与 `step12_dbq_spec.json` 的命中块同源；v2 之后才出现 ORD-004/ORD-005。
- 稠密向量是 `embedding.py` 里的确定性哈希 n-gram（256 维）实现，注册为 pyseekdb 的 `EmbeddingFunction`；不下载模型，保证干净环境离线可复现。

**查证过程（读源码/文档所得，影响设计）**：`pyseekdb` 的 `hybrid_search` 要求 `query`（全文 `$contains`）与 `knn`（`query_texts`）并存、`rank` 支持 `{"rrf": {...}}`；`Schema` 必须显式给出 `VectorIndexConfig.hnsw.dimension`，因此向量维度固定为 256；全文索引分析器可选 `ik`（中文按词切分），这是中文规格能被全文命中的前提。

## 2. PowerContext 的使用（任务状态存储与跨进程复用）

**用法**：模块自身不写任何本地状态文件；保存与读取统一走 PowerContext Server 的 atomic-memory API。

| 环节 | PowerContext 接口 | 代码位置 | 证据 |
|---|---|---|---|
| 启动服务 | `powercontext server run --host 127.0.0.1 --port 18081`，`POWERCONTEXT_HOME` 指向 `minimax/.pcserver/home` | `scripts/start_server.sh` | `.pcserver/server.log`、`step11` 重启后仍可读 |
| Scope | `POST /v1/scopes`（固定 `idempotency_key="minimax-sdd-scope-v1"`，任何新进程解析到同一 Scope）；失败退回 `GET /v1/scopes/default` | `sdd_context/state.py::ensure_scope` | `step7/10/11` 的 `scope_id` 相同 |
| 写状态 | `POST /v1/memory/remember`，`kind="task_state"`，text 为 `TaskRecord` JSON | `state.save` | `step7_state_planned.json`、`step10_state_verified.json` |
| 读状态 | `POST /v1/memory/search`（按 task_id 检索，取 `updated_at` 最新） | `state.search` / `state.latest` | `step11_state_show_after.json` |
| 审计 | `POST /v1/memory/entries/list`（Scope 内全部 task_state 记录，供核对） | `state.audit_dump` | `step1/step11` 的 `scope_task_state_entries` |
| 参与后续处理 | `context_builder._read_task_state` 把 `phase/done/todo/results` 注入上下文并渲染给 MiniMax | `context_builder.py` | `step11_context_final.md` 的「任务状态（来自 PowerContext）」段 |

**空状态起步 → 复用**：`FRESH_PC=1` 先删 `.pcserver/home`（step1 `state show` 返回退出码 3、`latest=null`）→ step7/step10 两次写入 → step11 `stop_server.sh` + `start_server.sh` **真实停启**后，新进程读到 `phase=verified`、`done` 5 项、`todo` 2 项、`results` 内含两套 `exit_code=0`，并出现在同一进程的上下文输出中（`records_found=2`）。

**查证过程**：`/v1/memory/remember` 的 `text` 上限为 8192 UTF-8 字节，故 `taskrecord.py` 依次裁剪 `notes` → `results`（并保留 `{"truncated": true, "keys": [...]}` 标记）；Server 的数据目录只认 `POWERCONTEXT_HOME`（`POWERCONTEXT_STORAGE_SQLITE_PATH` 无效），因此脚本统一导出该变量，保证状态库随作品目录走、删除即回到空状态。

## 3. MiniMax 的使用（真实参与代码修改）

**用法**：`sddctx patch` 把 step6 的结构化上下文渲染成 Markdown 交给 MiniMax，模型返回「整文件内容」JSON，`patcher.py` 校验后落盘。

| 环节 | 内容 | 证据 |
|---|---|---|
| 请求 | `POST {MINIMAX_BASE_URL}/chat/completions`，`Authorization: Bearer $MINIMAX_API_KEY`（只在运行时读环境变量，不写入任何文件/证据），`temperature=0.1`，`max_tokens=16000` | `step8_minimax_run.json` → `endpoint` / `model` |
| 送入的上下文 | `context_markdown`：任务描述 + 10 条适用规格（含来源路径）+ 待改代码当前内容 + 目标/回归测试用例与内容 + 来自 PowerContext 的任务状态 + 来源核验结论 | `step8_minimax_run.json` → `context_markdown`（与 `step6_context_specv2.md` 同源） |
| 约束 | system 提示要求：只改上下文中列出的代码文件、不得新增文件、不得改测试与规格、必须满足每条规格并保持回归约束 | `minimax_client.py::SYSTEM_PROMPT` |
| 模型输出 | 原样保存的 `raw_model_output`（```json 围栏 + 整文件内容）与服务端 `usage` | `step8_minimax_run.json` → `raw_model_output` / `usage` |
| 落地为代码差异 | `patcher.apply_change`：路径越界拒绝 → 白名单（上下文中的 `code_targets`）校验 → 原文件备份到 `.sdddata/backups/<时间戳>/` → 写盘 → `difflib.unified_diff` | `step8_code_diff.patch`、`code_before/`、`code_after/`、`apply_result.backup_root` |

**开发记录 ↔ 代码差异对应**：`context_markdown`（依据）→ `raw_model_output`（过程）→ `step8_code_diff.patch` + `code_after/`（结果）→ 仓库内 `demo_project/src/order_service/service.py`（提交代码）。三者是同一份内容的不同呈现，可用 `验证样例.md` 第 4 节最后一条 `diff -u` 命令直接核对（应无差异）。

## 4. 开发过程记录（含返工与修正）

1. **样例设计**：以「订单服务的查询能力演进」为载体，刻意让任务描述不含接口细节，把 ORD-004/ORD-005 只写进 v2 规格；把退款边界（REF-001/002）与金额/枚举约束（ORD-CORE-*）留在回归范围，使「上下文正确」与「代码修改有效」两项能被同时证伪与证实。
2. **修改前必须功能性失败**：初版目标测试引用了尚不存在的模块路径，可能以 `ImportError` 形式“假失败”。改为只使用工程内已有的 `order_service.models/service` 可导入名称，确认失败原因是 `TypeError: list_orders() got an unexpected keyword argument 'status'`（step3 全量 6 例失败、回归 8 例通过）。
3. **检索质量调优**：纯向量对小库召回不稳 → 改为 seekdb 混合检索（全文 `$contains` + HNSW 向量 + RRF），并加「同规格文件整体扩展」与「规格内 `关联代码/验证` 引用定位」两级补充；验证点是 step4 能在 8 条规格之外稳定带出 `service.py`、两个测试文件。
4. **状态写入超限**：把整份 verify 报告塞进 `task_state` 触发 8192 字节上限 → `TaskRecord.to_text` 增加分级裁剪；`state save --results-file` 保留关键 `suites/exit_code`。
5. **脚本假失败问题**：`_lib.sh` 原先 `set -e` 导致预期失败步骤中断整个流程；改为 `set -uo pipefail` + `run` / `run_expected_fail` 双封装，step1（空状态 exit 3）与 step3（修改前 exit 1）作为预期结果不计入异常，正常全跑 `FAILED=0`、脚本退出码 0。
6. **PowerContext 数据目录**：曾误用 `POWERCONTEXT_STORAGE_SQLITE_PATH`（无效，状态落到 `~/.local/share/powercontext`）→ 改为 `POWERCONTEXT_HOME=minimax/.pcserver/home`，并在 `run_demo.sh` 中以 `FRESH_PC=1` 演示真正的空状态起步。
7. **证据可核对性**：`verify` 增加 `--out-dir` 落盘原始 pytest 输出与 `verify_{label}.json`；`snapshots.py` 由 step8 记录展开 `code_before/`、`code_after/`；step11 改为真实 `stop/start` Server 而非仅新建 CLI 进程；step9 额外产出 `step9_code_after.tar.gz`。
8. **流程彩排**：用本地假端点（返回一份 v2 目标实现）跑通 step1–12 两次，确认步骤编排、证据落盘与退出码语义正确后，删除彩排产物、用真实 Key 重跑本文件第 0 节的登记项。
